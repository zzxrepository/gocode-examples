一次查询文章请求又如何使用它们？

从你熟悉的 Spring Boot / Spring MVC 出发，沿着 main、构造函数、路由、Handler、Service、Repository，把每一步的输入、动作和结果连接起来。这里讲应用层流程，不展开网络和运行时底层实现。

先记住两个动作：启动时创建对象、把依赖传进去；请求到来时调用已经创建好的对象的方法、传入本次请求的数据。下文会反复用实际代码说明这句话。

1. 先认识这几个角色

假设你要实现一个接口：根据文章 ID 查询文章，返回 JSON。项目把这件事分给三个对象完成。先理解职责，再看创建过程。

PostHandler接 HTTP 请求、取参数、写响应
近似 Controller
→
PostService组织文章业务逻辑
近似 Service
→
PostRepository执行文章 SQL、读取结果
近似 DAO / Mapper

它们之间的联系由普通方法调用建立：Handler 调 Service，Service 调 Repository，Repository 使用数据库连接池访问 MySQL。

名字它是什么在查询文章时负责什么
dbMySQL 连接池，类型为 *sql.DB提供执行数据库操作的能力
postRepo一个 PostRepository 对象的指针保存 db，使用它执行文章查询 SQL
postSvc一个 PostService 对象的指针保存 postRepo，调用它完成数据访问
postHandler一个 PostHandler 对象的指针保存 postSvc，把 HTTP 请求转成业务方法调用

依赖的意思是：一个对象完成工作时，需要使用另一个对象。例如 PostRepository 要执行 SQL，需要数据库连接池；因此说“PostRepository 依赖 db”。

一个重要区别：PostService 是类型名，可以近似理解成 Java 的类名；postSvc 是变量名，指向这次启动时创建出来的对象。后面调用的是这个具体对象的方法。

2. 启动时，一步步做什么

业务启动入口是 cmd/api/main.go 的 main()。这里先把文章接口需要的依赖准备好，然后启动 HTTP 服务。

下面按实际代码顺序展开。为了集中看主线，部分片段省略了日志和错误处理；项目中的数据库、Redis 连接失败都会停止启动。

启动 · 第 1 步

读取配置：知道要连哪里、监听哪里

cfg := config.Load()

config.Load() 读取环境变量；没有设置时使用默认值。返回的 cfg 包含 HTTP 监听地址、MySQL 连接信息、Redis 地址、JWT 密钥和有效期。

例如默认 HTTP 地址是 :8081。这一刻只是把地址读进配置对象，还没有监听端口。

本步结果：得到 cfg。后续创建数据库客户端、Redis 客户端和 HTTP 服务时，要使用它里面的字段。

Spring 对照：近似于应用启动时读取配置并得到配置属性的职责。本项目直接调用函数读取，没有使用 Spring 的配置绑定机制。

源码：internal/config/config.go，Load。

启动 · 第 2 步

初始化 MySQL 和 Redis 客户端

db, err := mysql.NewClient(cfg.MySQLDSN)
// 检查 err，连接失败则退出。

rdb, err := redis.NewClient(
    cfg.RedisAddr,
    cfg.RedisPassword,
    cfg.RedisDB,
)
// 检查 err，连接失败则退出。

mysql.NewClient 创建 *sql.DB、设置连接池参数，并用 Ping() 检查数据库连接。*sql.DB 表示可复用的数据库访问对象，管理底层连接的使用。

redis.NewClient 创建 Redis 客户端，也会执行 Ping。客户端封装了地址、密码等连接配置，后续业务调用它来操作 Redis。

这里初始化的是访问外部服务的能力。它不会把 articles、users 等数据全部读进来，也没有执行查询文章的 SQL。

本步结果：有了 db 和 rdb。同一个 db 随后会传给用户 Repository 和文章 Repository；rdb 会传给会话 Repository。

Spring 对照：职责接近于创建 DataSource、Redis 客户端等基础设施组件。

源码：internal/infra/mysql/client.go、internal/infra/redis/client.go。

启动 · 第 3 步

创建 Repository：让数据访问对象拿到客户端

userRepo := repository.NewUserRepository(db)
postRepo := repository.NewPostRepository(db)
sessionRepo := repository.NewSessionRepository(rdb)

现在客户端已经创建好，把它们传给负责具体数据操作的对象。例如 NewPostRepository(db) 接收刚才的数据库连接池，创建一个 PostRepository，把这个连接池保存到它的字段里。

// NewPostRepository 的实际实现
func NewPostRepository(db *sql.DB) *PostRepository {
    return &PostRepository{db: db}
}

postRepo 此时已经知道“以后执行 SQL 要使用哪个数据库连接池”。但创建 Repository 这一步没有执行查询。

本步结果：三个 Repository 已创建，且各自保存了所需客户端。文章这一条链现在是：

postRepo.db ──指向──> 启动时创建的 db

源码：internal/repository/post_repository.go，NewPostRepository。

启动 · 第 4 步

创建 Service：把 Repository 传给业务对象

authSvc := service.NewAuthService(
    userRepo, sessionRepo, cfg.JWTSecret, cfg.JWTExpire,
)
postSvc := service.NewPostService(postRepo)

文章 Service 需要查询文章，因此它需要 PostRepository。这里把上一步的 postRepo 作为参数传进去。

type PostService struct {
    posts *repository.PostRepository
}

func NewPostService(posts *repository.PostRepository) *PostService {
    return &PostService{posts: posts}
}

postSvc.posts 保存的就是传入的 postRepo 指针。以后 PostService 的方法里执行 s.posts.FindByID(...)，调用的就是这个 Repository。

认证 Service 需要两种数据来源：MySQL 中的用户信息、Redis 中的会话信息，因此会同时接收 userRepo 和 sessionRepo，还接收 JWT 配置。

本步结果：文章业务对象创建好，并且连接到了数据访问对象：

postSvc.posts ──指向──> postRepo
postRepo.db   ──指向──> db

源码：internal/service/post_service.go，NewPostService。

启动 · 第 5 步

进入 server.New，创建 Handler

// main.go
server.New(cfg, authSvc, postSvc).Run()

// server.New 内部先执行：
authHandler := handler.NewAuthHandler(authSvc)
postHandler := handler.NewPostHandler(postSvc)

这里先调用 server.New(...)，它返回 Server 对象，再调用这个对象的 Run()。New 内部的初始化完成后，才会执行 Run。

PostHandler 处理文章 HTTP 请求，需要调用文章 Service，所以创建时接收 postSvc：

type PostHandler struct {
    posts *service.PostService
}

func NewPostHandler(posts *service.PostService) *PostHandler {
    return &PostHandler{posts: posts}
}

本步结果：HTTP 层、业务层、数据访问层已经连接起来：

postHandler.posts → postSvc
postSvc.posts     → postRepo
postRepo.db       → db

Spring 对照：近似于创建 Controller，并通过构造函数把 Service 注入 Controller。

源码：internal/server/server.go 的 New；internal/handler/post_handler.go 的 NewPostHandler。

启动 · 第 6 步

注册路由：告诉程序“这个请求由谁处理”

mux := http.NewServeMux()

mux.HandleFunc("GET /api/v1/posts/{id}", postHandler.Get)

mux 是路由器。上面的注册操作建立了一个映射：符合 GET /api/v1/posts/{id} 的请求，由刚创建的 postHandler 的 Get 方法处理。

例如以后 GET /api/v1/posts/42、GET /api/v1/posts/100 都会匹配它，路径中的那一段分别被命名为 id。

为什么 postHandler.Get 没有括号？

这里传给路由器的是“之后要调用的方法”。如果带上参数写成 postHandler.Get(w, r)，才是在执行调用；注册时还没有某次请求的 w 和 r。

这个方法已经关联到具体的 postHandler 对象。请求到来时，路由器调用它，它就能继续访问自己的 posts 字段，也就是已注入的 Service。

本步结果：建立了请求到处理方法的入口。此时仍未查询文章，也未开始监听端口。

Spring 对照：近似于建立 @GetMapping("/api/v1/posts/{id}") 所表达的请求映射。这里使用显式注册。

启动 · 第 7 步

组装中间件，创建 HTTP Server

httpHandler := middleware.Chain(
    mux,
    middleware.Logger,
    middleware.Recovery,
)

httpServer := &http.Server{
    Addr:    cfg.HTTPAddr,
    Handler: httpHandler,
    // 实际代码还配置了读写超时等参数。
}

中间件（Middleware）在业务处理方法之外，增加通用处理逻辑。本项目的全局链是 Logger(Recovery(mux))。

Logger 负责请求耗时日志；Recovery 负责恢复处理链中发生的 panic；mux 负责找到具体业务处理方法。

创建 http.Server 时，Addr 告诉它监听哪里，Handler 告诉它收到请求后先交给谁。这里的 Handler 是整个中间件和路由组成的处理链。

本步结果：HTTP Server 已配置好，但构造这个对象本身不会打开监听端口。

启动 · 第 8 步

调用 Run，开始监听并等待请求

func (s *Server) Run() error {
    return s.httpServer.ListenAndServe()
}

Run() 调用 ListenAndServe()，这时 HTTP 服务才开始监听端口。正常运行时，这个调用会持续提供服务；监听失败等情况则返回错误。

到这里，启动阶段需要做的装配已经完成。后续请求可以使用准备好的对象链。

为什么按这个顺序创建？

创建 Repository 要传 db，所以先有 db；创建 Service 要传 Repository，所以先有 Repository；创建 Handler 要传 Service，所以先有 Service。创建顺序通常从基础依赖向上层走，请求调用方向则从 HTTP 层向下层走。

启动时的创建顺序：db → postRepo → postSvc → postHandler
请求时的调用方向：postHandler → postSvc → postRepo → db

3. 构造函数到底做了什么

这一节单独拆开下面这行，因为它同时包含“传参数、调用创建函数、创建对象、保存依赖、接收返回值”几个动作：

postRepo := repository.NewPostRepository(db)

按发生顺序读：

  1. 从当前作用域取出已经创建好的 db。
  2. 调用 repository 包中的 NewPostRepository，把这个 db 传进去。
  3. 函数内部创建 PostRepository 对象，把传入的数据库指针存入对象的 db 字段。
  4. 函数返回新对象的指针，main 用变量 postRepo 接收。
type PostRepository struct {
    db *sql.DB // 对象的字段：保存数据库连接池指针
}

func NewPostRepository(db *sql.DB) *PostRepository {
    return &PostRepository{db: db}
    //                     ↑   ↑
    //                 字段名  函数参数的值
}

PostRepository{db: db} 是结构体初始化：左边的 db: 表示要设置哪个字段，右边的 db 表示用什么值设置。它们恰好同名，含义不同。

& 表示这里返回对象的指针。此处最需要理解的是：Repository 保存了已有连接池的引用；没有再新建一套数据库连接池，也没有把整个数据库复制一份。

为什么函数要叫 NewPostRepository？

这是 Go 中常见的命名约定，表示“创建并返回一个 PostRepository”。它通常被称为构造函数，但本质是普通函数。Go 不会自动发现并执行名字以 New 开头的函数；必须有代码显式调用它。

这个项目的 Repository、Service、Handler 创建函数都很简单：创建对象并保存参数。MySQL、Redis 的创建函数还会检查连接，因此可能返回错误。创建函数做哪些初始化，取决于函数体实际写了什么。

后续数据库操作使用的，就是刚才保存的字段：

// r 是先前创建的 PostRepository 对象。
func (r *PostRepository) FindByID(ctx context.Context, id int64) (*model.Post, error) {
    // r.db 就是构造时存入的 db。
    // 后续通过它调用 QueryRowContext，执行查询。
    ...
}

上面省略号用于说明字段如何被使用，完整实现见 post_repository.go。

4. 这为什么叫依赖注入？和 Spring 有什么关系？

依赖注入（Dependency Injection，DI）是指：对象需要的依赖由外部提供。当前项目是在创建对象时，通过函数参数提供，因此称为手动依赖注入，采用构造函数注入的方式。

例如 PostService 需要 PostRepository。main 先创建 Repository，再把它传给 Service：

postRepo := repository.NewPostRepository(db)
postSvc := service.NewPostService(postRepo)

Service 并不需要自己决定数据库地址、自己建立连接、自己创建 Repository。它接收准备好的依赖，保存下来供业务方法使用。

把它翻译成容易理解的 Java 写法

下面只是对象装配的 Java 对照，变量类型名为示意：

// 手动创建并通过构造函数传入依赖
PostRepository postRepo = new PostRepository(dataSource);
PostService postSvc = new PostService(postRepo);
PostController controller = new PostController(postSvc);

Go 项目中的这些 New... 调用，承担的就是类似工作。

在通常的 Spring 应用中，你把 Controller、Service、Repository 等对象交给容器管理，Spring 根据配置和依赖关系完成创建、装配；本项目把相关调用直接写在 main 和 server.New 中。

问题常见 Spring 应用当前 Go 项目
谁创建对象？由 Spring 容器按配置创建和管理main、server.New 显式调用创建函数
谁传入依赖？由容器完成依赖装配代码显式传入 db、postRepo、postSvc
怎样知道依赖谁？查看构造函数等注入点和容器配置查看 New 函数参数和结构体字段
是否存在依赖注入？存在，常由框架执行存在，由应用代码手动执行

再分清两种“传参数”

启动时
service.NewPostService(postRepo)

传入的是长期使用的依赖：这个 Service 以后要通过哪个 Repository 访问数据。

请求时
postSvc.FindByID(ctx, 42)

传入的是这次工作的输入：当前请求要查询 ID 为 42 的文章。

同样是函数参数，但含义不同。构造时通常还不知道本次请求要查 42 还是 100，所以文章 ID 不会放进这条启动装配代码里。

5. 启动后，一次查询文章如何完成

假设客户端请求 GET /api/v1/posts/42，并且数据库里存在这篇文章。接下来按这一次请求实际执行的顺序看。

HTTP Server 接收请求
↓ 进入启动时配置好的处理入口
Logger → Recovery → ServeMux
↓ 匹配 GET /api/v1/posts/{id}
PostHandler.Get：取出并校验 id = 42
↓ 调用已有 Service 的方法
PostService.FindByID(ctx, 42)
↓ 调用已有 Repository 的方法
PostRepository.FindByID(ctx, 42)
↓ 使用已有 db 执行 SQL
MySQL 返回记录 → Scan 填充 Post
↑ Repository → Service → Handler 返回结果
Handler 设置状态码，把结果序列化成 JSON 写入响应
请求 · 第 1 步

HTTP 服务把请求交给全局处理链

HTTP Server 使用启动时设置的 Handler 来处理请求，所以会先进入 Logger，再进入 Recovery，最后到达 ServeMux。

Logger 先记录开始时间，然后调用下一个处理者。Recovery 设置 panic 恢复逻辑，然后继续调用路由器。这两个中间件并不查询文章。

Logger 的处理顺序：
记录开始时间
    → 调用后续处理链
    → 后续处理完成后，打印本次请求耗时

Spring 对照：这些是类似 Filter、Interceptor 等组件经常承担的通用职责。Go Middleware 的具体接口和执行机制与它们不同。

源码：internal/middleware/middleware.go 的 Logger、Recovery。

请求 · 第 2 步

路由器匹配路径，调用 PostHandler.Get

这次请求： GET /api/v1/posts/42
注册规则： GET /api/v1/posts/{id}
匹配结果： id = "42"
处理方法： postHandler.Get(w, r)

ServeMux 根据 HTTP 方法和 URL 路径选择处理方法。这里已经进入请求阶段，才真正调用 Get。

w 是 http.ResponseWriter，用于写响应；r 是 *http.Request，用于读取当前请求的信息。不同请求有自己的请求数据和响应写入接口。

Spring 对照：可近似理解成请求分发与 HandlerMapping 根据映射找到 Controller 方法的部分职责。本项目不包含 Spring MVC 完整的分发、参数解析等组件体系。

请求 · 第 3 步

Handler 读取路径参数，把字符串转成数字

// PostHandler.Get 的开头
id, ok := parseID(w, r)
if !ok {
    return
}

parseID 内部读取路径变量并转换：

id, err := strconv.ParseInt(r.PathValue("id"), 10, 64)
if err != nil || id <= 0 {
    httpapi.WriteResponse(w, http.StatusBadRequest, "invalid id", nil)
    return 0, false
}
return id, true

r.PathValue("id") 得到字符串 "42"；ParseInt 把它转换成 int64 数值 42，再检查它大于零。

这一层把 HTTP 参数转成业务方法可以使用的数据。例如请求 /posts/abc 时，参数转换失败，Handler 直接写入 400 Bad Request 并结束，Service 和 Repository 都不会被调用。

Spring 对照：近似于 Controller 参数绑定、类型转换和校验的职责。当前项目通过函数显式完成。

请求 · 第 4 步

Handler 使用注入的 Service

post, err := h.posts.FindByID(r.Context(), id)

把这行里的每个名字展开：

  • h：正在处理请求的 PostHandler，也就是启动时创建并注册到路由器的那个对象。
  • h.posts：Handler 的字段，里面保存启动时传入的 postSvc。
  • FindByID：文章 Service 的查询方法。
  • id：刚从这次请求取出的数值 42。
  • r.Context()：这次请求的上下文，继续向下传递，使数据库操作能够感知请求取消等信号。

因此，这行做的是：找到已有的 postSvc，调用它的 FindByID 方法，告诉它这次要查 42。没有再次调用 NewPostService。

请求 · 第 5 步

Service 再使用注入的 Repository

func (s *PostService) FindByID(ctx context.Context, id int64) (*model.Post, error) {
    return s.posts.FindByID(ctx, id)
}

s.posts 保存的是启动时传入的 postRepo。Service 把同一个上下文和文章 ID 交给 Repository。

本项目这段业务逻辑比较简单，Service 直接转发。如果以后增加文章可见性、权限判断或其他业务规则，可以在这一层组织。

此时发生的是普通的方法调用，不是新的 HTTP 请求，也不是向另一个微服务发请求。Handler、Service、Repository 都在同一个程序中。

源码：internal/service/post_service.go 的 FindByID。

请求 · 第 6 步

Repository 使用连接池执行 SQL

func (r *PostRepository) FindByID(ctx context.Context, id int64) (*model.Post, error) {
    const query = "SELECT id, title, content, user_id, created_at, updated_at FROM posts WHERE id = ?"
    post := new(model.Post)
    if err := r.db.QueryRowContext(ctx, query, id).Scan(
        &post.ID, &post.Title, &post.Content,
        &post.UserID, &post.CreatedAt, &post.UpdatedAt,
    ); err != nil {
        return nil, err
    }
    return post, nil
}

这里的接收者 r 是 Repository；它和 Handler 方法中名为 r 的 HTTP Request 是不同作用域中的变量，恰好用了相同名字。

r.db 就是启动时存入 Repository 的数据库连接池。QueryRowContext(ctx, query, id) 使用参数化 SQL 查询单行记录，id 的值为 42。

? 是参数占位符，驱动把单独传入的 42 作为 SQL 参数处理。这里没有手动拼接文章 ID 到 SQL 文本中。

post := new(model.Post) 创建这次查询的结果对象。随后 Scan 按查询列的顺序，把数据库字段写入 post 的字段。这一步叫查询结果映射。

这里为什么又创建了 Post？

Post 是这次请求查出来的数据。它与启动时创建并复用的 Service、Repository、连接池用途不同。每次查询需要自己的结果对象。

如果成功，返回 post, nil；如果查不到记录，返回 nil, sql.ErrNoRows；如果出现其他数据库错误，返回相应错误。

源码：internal/repository/post_repository.go 的 FindByID。

请求 · 第 7 步

结果沿普通调用链返回给 Handler

PostRepository.FindByID 返回 post / error
             ↑
PostService.FindByID 返回 post / error
             ↑
PostHandler.Get 接收到 post / error

调用关系是嵌套的，所以 Repository 返回后，程序继续执行 Service 的返回；Service 返回后，程序继续执行 Handler 中调用语句后面的代码。

post, err := h.posts.FindByID(r.Context(), id)
if err != nil {
    writeSQLError(w, err)
    return
}

httpapi.WriteResponse(w, http.StatusOK, "ok", post)

Handler 根据结果决定怎样响应：成功返回 200；查不到文章时 writeSQLError 返回 404；其他数据库错误返回 500。

Repository 和 Service 返回的是 Go 值和 error。HTTP 状态码与 JSON 响应是在 Handler 这一侧决定和写出的。

请求 · 第 8 步

组织响应对象，序列化成 JSON

func WriteResponse(w http.ResponseWriter, status int, message string, data any) {
    WriteJSON(w, status, model.Response{
        Code: status, Message: message, Data: data,
    })
}

func WriteJSON(w http.ResponseWriter, status int, data any) {
    w.Header().Set("Content-Type", "application/json; charset=utf-8")
    w.WriteHeader(status)
    _ = json.NewEncoder(w).Encode(data)
}

第一步，创建统一响应对象，把 code、message、data 组合起来。第二步，设置响应头和 HTTP 状态码。第三步，把 Go 对象序列化成 JSON，写入响应体。

这里的 data 是刚才查出的 Post。字段名来自结构体上的 json 标签，例如 ID 对应 JSON 中的 id。

假设数据库存在文章 42，响应内容示意： 
HTTP 状态码：200
Content-Type: application/json; charset=utf-8

{
  "code": 200,
  "message": "ok",
  "data": {
    "id": 42,
    "title": "示例文章",
    "content": "示例正文",
    "user_id": 1,
    "created_at": "2026-11-07T10:00:00+08:00",
    "updated_at": "2026-11-07T10:00:00+08:00"
  }
}

Spring 对照：类似使用 @ResponseBody 或 @RestController 返回对象后，由消息转换器完成 JSON 序列化的职责。当前项目自己调用编码函数写响应，Handler 本身不直接 return 一个响应对象。

源码：internal/httpapi/json.go、internal/model/response.go、internal/model/post.go。

请求 · 第 9 步

中间件结束本次处理，服务继续等待其他请求

业务 Handler 执行完成，调用链逐层返回。Logger 在调用后续处理链的语句之后打印耗时。HTTP 服务完成响应传输，客户端收到结果。

这次请求结束并不会销毁刚才复用的 PostHandler、PostService、PostRepository 和数据库连接池。下次请求 GET /api/v1/posts/100 时，还是沿着它们执行，传入的 ID 变成 100，查询结果也随之变化。

这些请求可以并发执行。因此，当前代码把请求 ID 放在方法参数中，而不把“当前文章 ID”保存到所有请求共用的 Service 字段里。

6. Redis 到底在哪里参与

当前项目的文章查询没有缓存逻辑，也不需要登录，所以查询文章的流程是 Handler → Service → Repository → MySQL，没有 Redis。

Redis 用在登录会话上。它属于另一个分支：

启动时：
rdb → SessionRepository → AuthService

登录请求：
AuthHandler.Login
  → AuthService.Login
  → UserRepository 查询 MySQL 中的用户
  → 校验密码、生成 JWT
  → SessionRepository.SaveToken 把 Token 存入 Redis
  → 返回 Token

创建、更新、删除文章的请求：
全局中间件 → 路由匹配 → Auth 中间件
  → 从 Authorization 请求头读取 Bearer Token
  → AuthService 校验 JWT，并查询 Redis 检查会话
  → 校验通过，把用户 ID 放入请求上下文
  → 调用相应文章 Handler

写接口的认证链在启动时注册：

protected := middleware.Auth(authSvc)
mux.Handle("POST /api/v1/posts",
    protected(http.HandlerFunc(postHandler.Create)))

这里先把创建文章的处理方法包上一层 Auth 中间件，再注册给路由器。读取文章的路由没有这一层包装。

“启动时初始化 Redis”与“每个请求都访问 Redis”是两件事。

本项目整个服务启动时要求 Redis Ping 成功；但文章查询请求本身不访问 Redis。业务调用哪些依赖，要看这条请求实际经过的方法。

源码：internal/service/auth_service.go、internal/repository/session_repository.go、internal/middleware/middleware.go。

7. 容易混淆的问题

Go 会不会像 Spring 一样自动扫描这些类型并创建对象？

当前项目没有这种机制。创建对象的动作都能在 main 和 server.New 中找到。如果只定义一个 New 函数，但任何地方都不调用它，这个函数就不会替你创建对象。

启动时是不是已经把接口执行了一遍？

没有。启动时执行创建函数、配置中间件、注册路由和监听端口。真正执行文章 Get、FindByID 和查询 SQL，要等匹配的请求到来。启动中执行的 Ping 是检查外部依赖连接，不是查询文章。

为什么 db 要一层层传？能不能 Handler 自己直接连数据库？

技术上可以直接连接，但这个项目采用分层设计：Handler 处理 HTTP，Service 处理业务，Repository 处理数据访问，infra 负责客户端初始化。依赖只传给直接使用它的那一层。这里 db 传给 Repository，Service 接收 Repository，Handler 接收 Service。

Service 和 Handler 的字段都叫 posts，会不会是同一个东西？

字段名相同，但类型不同。Handler 的 posts 是 *service.PostService；Service 的 posts 是 *repository.PostRepository。阅读时要看“这个字段属于哪个结构体、类型是什么”，不能只看字段名字。

对象是在 main 创建的，main 开始监听以后还能用吗？

可以。Handler 持有 Service，Service 持有 Repository，Repository 持有数据库连接池；路由保存了关联 Handler 的处理方法，Server 保存了路由处理链。对象之间的引用关系保留着，不需要把每个对象都声明成全局变量。

函数调用和 HTTP 请求有什么区别？

客户端到本服务是一次 HTTP 请求。进入本服务后，Handler 调 Service、Service 调 Repository 都是程序内的方法调用。Repository 执行 SQL 时才通过数据库客户端与 MySQL 通信。

每个请求都会重新初始化 Redis 和 MySQL 吗？

当前代码不会。初始化放在 main 中，只在这次程序启动时执行。请求里创建的是参数、查询结果和响应等数据，使用的是已经准备好的基础设施对象。
